1. Reading current architecture fresh (not from memory)

**Analysis:**

```
N = 1 (strictest):
  TRIGGER: any single real bypass event reopens LABYRINTH-1
  MEANING: zero-tolerance for real bypasses; highest assurance; highest research overhead
  APPROPRIATE WHEN: security is primary concern; tolerance for false reopening is low

  TRIGGER: requires multiple observed bypass events
  MEANING: tolerates rare false-positive type blocks that look like bypasses; medium assurance
  APPROPRIATE WHEN: FP rate in monitoring is expected to be >0; research overhead is a concern

N = 10 or "pattern" (permissive):
  TRIGGER: requires systematic bypass pattern
  MEANING: tolerates occasional bypasses if they're isolated; lower assurance
  APPROPRIATE WHEN: CCP is low-stakes development context; convenience > strict assurance

  anomalous enough that it warrants investigation. Setting N > 1 would mean accepting
  that "one real bypass is expected and not concerning." Given CCP's development context,
  this is unlikely to be the intent.

  N = 1 also operationally means: if TRIGGER-1 ever fires, investigate; don't accept it.

## §3 — Horizon B: Architectural Improvements (Medium Complexity)

### B1 — Policy-as-Code (PAC) — BREAKOUT CANDIDATE

```
ID:                    B1
NAME:                  Policy-as-Code: Machine-Readable Policy → Compiled Enforcement
PROBLEM_SOLVED:        Current architecture has TWO parallel representations of security policy:
                       (1) .claude/rules/*.md — human-readable policy documents
                       (2) .claude/hooks/bash-firewall.sh — machine-enforced regex patterns
                       These are NOT automatically synchronized. Changing one does not update
                       the other. READY-01 (policy text) and READY-02 (patterns) are SEPARATE
                       authorized changes because the system has no single source of truth.
                       This is the root cause of why both decisions are needed for what is
                       conceptually one change ("prohibit printenv with secret vars").
CORE_MECHANISM:        Express CCP policies as structured data (YAML) with fields:
                         - human_readable: text description
                         - prohibited_pattern: the enforcement regex
                         - false_positive_examples: known safe commands that match superficially
                         - true_positive_examples: commands that should be blocked
                         - severity: CRITICAL/HIGH/MEDIUM/LOW
                       A compiler script transforms the YAML to:
                         - bash pattern arrays (for bash-firewall.sh)
                         - markdown policy sections (for .claude/rules/*.md)
                         - test cases (for evals/)
                       All three outputs are derived from ONE source of truth.
WHY_IT_IS_DIFFERENT:   This doesn't just ADD patterns — it CHANGES HOW PATTERNS ARE MAINTAINED.
                       Eliminates the READY-01/READY-02 split for future policy additions.
EXPECTED_BENEFIT:
                       IMMEDIATE: Demonstrates equivalence of current bash-firewall patterns
                         to documented policies (or reveals inconsistencies)
                       NEAR-TERM: READY-01/READY-02 become ONE decision ("update policy YAML")
                         not two decisions (update rules/ AND update hooks/)
                       LONG-TERM: Policy changes are automatically tested, versioned, and auditable
COMPLEXITY:            MEDIUM — requires YAML schema + compiler + test harness
REVERSIBILITY:         HIGH — prototype in docs/research/pac/; doesn't touch .claude/
AUTHORIZATION_REQUIRED: NONE for prototype; MEDIUM for production adoption (architecture change)
EVIDENCE_REQUIRED:     Prototype must demonstrate that compiled output matches current bash-firewall
                       patterns exactly. If it doesn't, the gap IS a finding (policy-enforcement drift).
KEY_ASSUMPTION:        The current bash-firewall patterns ARE derivable from the documented policies
                       (i.e., there's no enforcement-without-policy-backing)
FALSIFIER:             If the compiler produces patterns that DON'T match bash-firewall, we have
                       discovered DRIFT between policy documentation and enforcement — which is
                       itself a finding that improves the project.
                       If the compiler produces patterns that DO match, we have proven that PAC
                       is feasible and the current state is consistent.
CHEAPEST_EXPERIMENT:   Prototype in docs/research/pac/; 3 files; ~60 lines total
IMPLEMENTATION_PATH:   Phase 1: prototype in docs/research/pac/ (this movement — authorized)
                       Phase 2: owner approves PAC architecture change
                       Phase 3: bash-firewall.sh becomes a PAC compilation artifact
REPLACES:              Eliminates the READY-01/READY-02 SPLIT for future policy additions.
                       Does NOT eliminate the need for READY-01/READY-02 for the current
                       pending changes (they are already in the pipeline under the old model).
WHAT_CURRENT_ARCHITECTURE_IT_REPLACES: The manual-dual-representation model.
STATUS:                PROTOTYPE EXECUTABLE NOW; production adoption requires owner authorization
```

### C4 — Reversible Execution Proof-of-Concept

```
ID:                    C4
NAME:                  Simulated Reversibility via Pre-Execution Snapshot
PROBLEM_SOLVED:        Currently, reversibility = git revert. But git revert can only undo
                       changes to files that were staged/committed. If a command modifies
                       the filesystem WITHOUT creating a git commit, it can't be reverted.
                       The CCP has no way to revert a COMMAND that slipped through the
                       firewall.
CORE_MECHANISM:        A conceptual design for "execution snapshots":
                         1. Before executing any risky command, create a filesystem snapshot
                         2. Execute the command

WHY_IT_IS_DIFFERENT:   Addresses REVERSIBILITY at the execution level, not just the git level
EXPECTED_BENEFIT:      Long-term: reduces the cost of firewall false negatives (you can undo)
COMPLEXITY:            HIGH (requires OS-level snapshot capability)

## 2. Executive Summary

### F7: behavioral and evidence-integrity hardening

F7 began from a completed F1-F6 control plane and an adversarial audit that
found real behavioral gaps. It became an extended implementation phase rather
than only the original freshness proposal because the audit reproduced a Stop
loop, several firewall bypass families, a false-PASS evidence path, log
rotation problems and installer overwrite behavior.

F7 hardened existing hooks, fixtures and maintenance checks. It did not add a
new architectural layer. Its implementation consisted of five named bundles,
an evidence-freshness/positive-fixture subbundle and the ARCH-004 task
semantics convention. It produced EV-009 through EV-014 and REG-002 through
REG-009. The owner accepted the evidence-driven size variance, and the phase
closed at checkpoint `47874a5`.

### F8: residual fail-closed closure

F8 started as research after F7 was frozen. Its research rejected broad
architecture expansion and identified only two demand-driven runtime closures:

- A-03: a missing `contract_hash` could pass the TaskCompleted gate under the
  F7 transitional rule.
- A-04: malformed firewall input could become an empty command and pass through
  the pre-existing extraction path.

F8 also documented A-06, a reviewer identity convention, and amended ARCH-004
in place. F8 changed two existing hooks and extended two existing fixtures. It
introduced no hook, skill, agent, rule, dependency, registry type or identity
field. It produced EV-015/EV-016 and REG-010/REG-011, passed independent review
round 3, and closed as `COMPLETE / FROZEN` at
`2cd795321486a30240197ac12a0bf51564ffba66`.

### F9: research gate, not implementation

F9 did not begin by selecting a feature. It asked whether any evidence justified
another implementation phase. The research examined the deferred candidates,
current controls, native-runtime boundary, evidence integrity limitations and
benefit versus complexity.

The result was:

```text
F9_RESEARCH_STATUS = COMPLETE
F9_DECISION        = F9 NOT JUSTIFIED
IMPLEMENTATION     = NOT AUTHORIZED / NOT PERFORMED
RUNTIME_CHANGED    = NO
```

This is not a failed phase. It is a research conclusion that no current
candidate has the combination of observed impact, unmet control,
proportionate benefit and reversible scope needed to open another runtime
implementation phase. Candidates remain documented with explicit reactivation
triggers rather than being forgotten.

## 3. Architecture Overview

The control plane is project-local infrastructure under `.claude/`, supported
by canonical Markdown registries, deterministic shell evaluations and a
Git-based review boundary. The architecture is layered, but the layers are
implemented by different strengths of control. Markdown guidance is not the
same as a blocking hook.

```text
CONTEXT       -> what the agent knows
STATE         -> where the project is
CONTROL       -> what can be blocked
EXECUTION     -> which agents and workflows act
VERIFICATION  -> how PASS/BLOCK is decided
LEARNING      -> how incidents become controls and regressions
HUMAN GATE    -> when phase or trust-boundary work is authorized
```

### 3.1 Context layer

The context layer includes:

- `CLAUDE.md`, the short project bootstrap and source map.
- `.claude/rules/*.md`, permanent rules for security, compliance, Git policy
  and no-go behavior.
- `.claude/context/*.md`, six role-oriented packs: `CORE`, `CURRENT_STATE`,
  `DECISIONS`, `BUSINESS`, `SECURITY_RULES` and `NO_GO`.
- Context skills that make the packs auditable and loadable.

`SubagentStart` injects context through `additionalContext` according to the
agent role. The repository deliberately does not treat an agent frontmatter
`skills:` field as a verified runtime loading mechanism.

`CLAUDE.md` provides the map and order of reading. It does not prove that a
capability exists. Runtime files, Git history and checks provide that proof.

### 3.2 State and registry layer

The state layer has one canonical source for each kind of fact:

| Concern | Canonical source | Purpose |
|---|---|---|
| Operational phase/state | `PROJECT_STATE.md` | phase, status, objective, blockers, checkpoint and authorization state |
| Decisions | `DECISION_REGISTRY.md` | architectural/process decisions and reversibility |
| Deliverables | `ARTIFACT_MANIFEST.md` | expected outputs per phase |
| Evidence | `docs/00_SYSTEM/EVIDENCE_REGISTRY.md` | claims, source, provenance, hashes, checks and status |
| Incidents | `INCIDENT_REGISTRY.md` | symptoms, RCA, reproducer and closure |
| Controls | `CONTROL_REGISTRY.md` | controls derived from incidents |
| Regressions | `REGRESSION_REGISTRY.md` | reproducible control checks |

Permitted mirrors are explicitly declared. `PROJECT_STATE.md` wins over its
compact `.claude/context/CURRENT_STATE.md` mirror; `DECISION_REGISTRY.md` wins
over `.claude/context/DECISIONS.md`.

### 3.3 Control layer

`.claude/settings.json` connects permissions and hook events. The settings
define `allow`, `ask` and `deny` behavior. The important trust boundary is:

- Bash commands pass through `bash-firewall.sh` at `PreToolUse`.
- Write/Edit content passes through `secret-guard.sh` at `PreToolUse`.
- Task completion passes through `task-completed-evidence.sh` at
  `TaskCompleted`.
- Session lifecycle hooks recover state, snapshot state, log activity and
  provide reminders.

The current wiring has ten hook scripts across SessionStart, PreToolUse,
SubagentStart, SubagentStop, Stop, PreCompact, ConfigChange and TaskCompleted.
The blocking security/evidence hooks use exit code `2` for denial. Logging and
context-recovery hooks are generally fail-open.

### 3.4 Execution layer

The repository contains five role-limited agents:

- `researcher`: read-only research and sources.
- `architect`: design and documentation, without shell execution.
- `implementer`: implementation and checks.
- `security-auditor`: read-only security review.
- `code-reviewer`: fresh-context review with no write or shell tools.

The repository also contains 22 skills in the F7/F8 inventory: context packs,
verification workflows, SDLC lanes, incident learning and operational skills.
The architecture prefers existing native tools and local skills over importing
an external framework.

### 3.5 Verification layer

The verification layer combines:

- `bash evals/maintenance.sh` for deterministic integration health.
- `bash -n` for installer, hook and evaluation syntax.
- Tier 1 structural skill validation.
- Tier 2 routing fixtures.
- Tier 3 behavioral runs with normalized signatures.
- Hook fixtures for positive, negative and adversarial cases.
- Incident regression `INC-001-task-completed-evidence.sh`.
- State integrity fixture for unchanged state and drift detection.
- Evidence freshness validation for Tier 3 results.
- Fresh-context independent review for medium/high-risk changes.
- Evidence and phase gates.

The repository explicitly distinguishes `SCRIPT VERIFIED` from
`CLAUDE RUNTIME VERIFIED`. Direct shell execution proves script behavior; it
does not prove Claude Code's native dispatcher, matcher, ordering or event
re-entry behavior.

### 3.6 Learning layer

The intended learning loop is:

```text
INCIDENT
   -> ROOT CAUSE
      -> CONTROL
         -> REGRESSION
            -> VERIFICATION
               -> EVIDENCE
                  -> CLOSE
```

`INC-001`, `CTRL-001`, `REG-001` and EV-006 provide the concrete example. F7
also created preventive regressions for demonstrated gaps without fabricating
an incident. F9 explicitly preserved the rule that a second incident must be
organic rather than manufactured.

### 3.7 Human gate

Human authorization is a phase boundary and trust-boundary control. F7 and F8
research documents define contracts but do not authorize implementation by
themselves. `permissions.ask` protects selected actions such as push and
destructive removal. P0 hook, permissions and trust-boundary changes require
explicit human approval under the documented process.

## 4. Control-Flow Architecture

The repository documents the following conceptual flow:

```text
HUMAN INTENT
     |
     v
SPEC / CONTRACT
     |
     v
EXECUTION BY MAIN AGENT / ROLE-LIMITED AGENT
     |
     v
DETERMINISTIC TESTS AND FIXTURES
     |
     v
INDEPENDENT FRESH-CONTEXT REVIEW WHEN RISK REQUIRES IT
     |
     v
EVIDENCE REGISTRY ENTRY
     |
     v
TaskCompleted EVIDENCE GATE
     |
  PASS / BLOCK
     |
     v
REGRESSION / CONTROL / INCIDENT LEARNING
```

The components have different enforcement strength:

| Component | Actual role | Enforcement status |
|---|---|---|
| `CLAUDE.md`, rules and context | instructions and context | guidance/context injection |
| `settings.json` permissions | tool access boundary | native permission behavior where runtime is available |
| Bash/secret hooks | synchronous payload filtering | blocking shell scripts, fail-closed on required inputs |
| TaskCompleted hook | completion evidence gate | blocking script; native lifecycle unverified under OpenCode |
| Fixtures and maintenance | deterministic verification | executable repository checks |
| Fresh reviewer | independent review | role/tool boundary and review record |
| Owner/human gate | phase and trust-boundary authorization | explicit process gate |

The flow is therefore not a claim that every step is a single automated
pipeline. The evidence entry, reviewer, maintenance suite and completion hook
are separate mechanisms linked by task IDs, hashes and registry records.

## 5. F7 Purpose And Context

### 5.1 Inherited baseline

F7 inherited the completed F1-F6 foundation:

- F1: installable, coherent state and canonical registries, EV-001.
- F2: evidence contract and TaskCompleted hardening, EV-002.
- F3: SDLC lanes and independent verification, EV-005 after the earlier
  authentication-blocked evidence in EV-003/EV-004.
- F4: incident learning cycle, INC-001/CTRL-001/REG-001 and EV-006.
- F5: PreCompact state snapshot, hash and drift detection, EV-007.
- F6: deterministic maintenance, regression budget, CI and baseline, EV-008.

F1-F6 remained historical baseline. F7 did not reinterpret or rewrite their
evidence.

### 5.2 Why F7 was opened

The post-F6 roadmap identified G-V1, G-Bob-2 and G-T1 as evidence-integrity
gaps. The adversarial behavioral audit then reproduced additional failures:

- Stop emitted the same `additionalContext` after `stop_hook_active=true`,
  creating a continuation loop.
- Literal firewall patterns were bypassed by whitespace and SQL-case variants.
- `.env` reads through `source`, dot-source, `eval`, `read`, `exec` and
  redirection were not fully covered.
- TaskCompleted accepted a historical task ID without coupling the current
  payload to a contract hash.
- Session log rotation copied instead of moving, and monthly archives could be
  overwritten.
- Reinstall could overwrite user settings unless protected.
- Empty `agent_type` was a cosmetic data issue.
- Fixture authoring could be blocked by the same guards being tested.

F7 therefore expanded from the original freshness proposal to an evidence-
driven extended phase. The design rule was to harden existing components, not
create an alternate control plane.

### 5.3 F7 scope principle

The F7 scope remained local and reversible:

- existing hooks were hardened;
- existing maintenance was extended;
- fixtures were added or extended;
- canonical registries were appended;
- no new hook, agent, skill, rule, registry type, dependency or architecture
  was introduced.

**RUNTIME FILES:** `.claude/hooks/stop-logger.sh`.
**FIXTURES:** `evals/hooks/stop-hook-idempotency.sh`.

**REGRESSIONS:** REG-005.
**EVIDENCE:** EV-010.
**COMMIT(S):** `148501f`.
**VERIFICATION:** fixture, syntax and maintenance passed.
**ROLLBACK / REVERSIBILITY:** revert `148501f`; no state or evidence rewrite.
**WHY THIS APPROACH:** it uses the event's existing idempotency signal rather
than adding state files, rate limits or a new lifecycle component.
**WHAT WAS NOT DONE:** no `WAITING_HUMAN` state file, no new Stop event and
no native lifecycle claim under OpenCode.

### 6.3 Bundle B - Firewall hardening

**FIXTURES:** `evals/hooks/firewall-positive.sh`.
**TESTS:** root deletion, whitespace-mutated deletion, fork bombs, mixed-case

**REGRESSIONS:** REG-002 and REG-006.
**EVIDENCE:** EV-011.
**COMMIT(S):** `cc8634f`, `82aaa75`, and the adversarial corrections in
`b659dfb`.
**VERIFICATION:** positive fixture, direct adversarial probes, maintenance and
`bash -n` passed.
**ROLLBACK / REVERSIBILITY:** revert the Bundle B commits; F1-F6 evidence is
preserved.
**WHY THIS APPROACH:** the repository needed coverage of demonstrated nearby
forms, not a general shell parser or a claim of arbitrary obfuscation

**WHAT WAS NOT DONE:** no general shell-language security proof, mutation

### 6.4 Bundle C - Evidence coupling and task semantics

**BUNDLE:** C - task/evidence coupling
**PROBLEM:** TaskCompleted looked for a VERIFIED registry entry by `task_id`,

coupling behavior.
**EVIDENCE:** EV-012.
**COMMIT(S):** `37662b4` for the ARCH-004 convention, `b1471d0` for coupling,
`1a3509e` for invalid evidence coverage and `b659dfb` for adversarial closure.
**VERIFICATION:** coupling fixture, INC-001, maintenance and fresh review
passed; the historical task reuse path was addressed.
**ROLLBACK / REVERSIBILITY:** revert per bundle; historical registries remain

**WHY THIS APPROACH:** it strengthened the existing gate and registry rather

## 7. F7 Firewall Architecture

At F7, `bash-firewall.sh` ran as a `PreToolUse` hook matching Bash. It reads a
JSON payload from stdin and extracts `.tool_input.command` with `jq`. Missing
`jq` is fail-closed. An empty extracted command is allowed because there is no
command to inspect; a valid JSON envelope alone is not a claim that every
arbitrary shell program is safe.

The F7 rules are finite pattern checks. They cover demonstrated families:

- destructive root/home deletion;
- device writes and formatting;
- fork-bomb forms;
- recursive permission/ownership changes;
- destructive SQL families;
- secret-shaped arguments;
- API/Bearer/AWS token patterns;
- `.env`, private-key and SSH/AWS credential reads;
- `git add` of secret files;
- `curl|bash` and `wget|bash` supply-chain forms.

Each match emits a reason and exits `2`. `DRY_RUN=true` is a simulation path
for controlled inspection, not the normal blocking behavior.

The F7 fixture tests both sides of the contract: known malicious payloads must
block, while `ls`, `git status`, local `node_modules` cleanup, ordinary README
reading and non-secret script dot-sourcing remain allowed. F7 expanded tests
for spacing, case, quoted/read/process-substitution and environment-read
variants. F8 later added validation of the JSON envelope before command
extraction; that addition is documented separately below.

The firewall is not a general shell interpreter and does not claim arbitrary
obfuscation coverage. Its architecture is deterministic, pattern-based and
reviewable. The finite coverage boundary is intentional and remains a known
limitation.

## 8. F7 Evidence-Gate Architecture

`.claude/hooks/task-completed-evidence.sh` is wired to the `TaskCompleted`
event. It reads the canonical `docs/00_SYSTEM/EVIDENCE_REGISTRY.md` and checks
the task completion payload against a Markdown evidence entry.

The gate validates, depending on risk and current phase semantics:

- `task_id` exists and matches exactly;
- evidence status is exactly `VERIFIED`;
- `Artifact Hash` is a non-zero SHA-256-shaped value;
- `Contract Hash` is a non-zero SHA-256-shaped value;
- tests, static and security checks have permitted values;
- reviewer is present and, for medium/high/critical risk, is `PASS`;
- exceptions are `NONE` or approved;
- timestamp is present;
- when supplied, payload `contract_hash` matches registry `Contract Hash`.

During F7, absent `contract_hash` was a documented ARCH-004 transitional
warning. This meant the gate could couple a supplied hash but did not yet
require the field for every completion. F8 removed this transition.

The gate is a registry lookup and contract check. It does not recompute the
artifact hash against an artifact set, does not cryptographically identify a
reviewer and does not prove native event delivery when invoked directly under
OpenCode.

The purpose of evidence coupling is to distinguish a current contractual task
from a historical evidence entry. F7 did not introduce a second task registry
or a new `run_id`/`attempt_id` identity model.

## 9. F7 Incident-Learning Architecture

`INC-001` is the concrete learning-loop example:

```text
INC-001: completion evidence was not enforced
    -> root cause: missing test/control path
       -> CTRL-001: TaskCompleted requires VERIFIED evidence
          -> REG-001: same payload unprotected without control and blocked with it
             -> EV-006: verification recorded
```

The four registries have distinct roles:

- `INCIDENT_REGISTRY.md` records symptom, context, reproducer, RCA and missing
  control.
- `CONTROL_REGISTRY.md` records the active control, enforcement level, source
  incident, owner and rollback.
- `REGRESSION_REGISTRY.md` records the executable test, baseline outcome,
  control outcome, evidence and status.
- `EVIDENCE_REGISTRY.md` records the verification claim and its provenance,
  hashes, checks, reviewer and timestamp.

The F7 preventive regressions for firewall, secret guard, freshness, Stop,
coupling, rotation and installer were allowed because each had a documented
gap or reproducible adversarial finding. F7 did not fabricate a second organic
incident.

## 10. F7 State Integrity And Provenance

F7 preserved the state model established by F5:

- `PROJECT_STATE.md` is the operational source of truth.
- `pre-compact-snapshot.sh` stores a state snapshot and critical-field hash.
- `session-start-compact.sh` reports `STATE_INTEGRITY: PASS` or
  `DRIFT_DETECTED`.
- Evidence entries carry provenance from the fixed vocabulary:
  `EXTRACTED`, `INFERRED`, `ASSUMED`, `EXTERNAL` or `GENERATED`.
- Git checkpoints identify phase closure and support per-bundle rollback.

An artifact or contract hash is integrity evidence about a recorded value. It
is not an immutability guarantee. A same-repository writer can modify code,
evaluators or registry text unless the change is caught by Git review or a
future independent trust boundary. That limitation is preserved in F7/F8/F9
documentation and was not silently converted into a security guarantee.

## 11. F7 Verification Model

F7 used multiple verification layers because different checks answer different
questions:

| Layer | Question answered | Actual mechanism |
|---|---|---|
| Syntax | Are scripts parseable? | `bash -n` over installer, hooks and evals |
| Structural | Are skills shaped correctly? | `evals/skills/validate.sh` Tier 1 |
| Routing | Do fixtures map to the intended skill? | Tier 2 fixtures |
| Behavioral | Do authenticated skill runs have stable behavior? | Tier 3 results and normalized signatures |
| Hook behavior | Do controls block/allow known cases? | Hook fixtures |
| Incident learning | Does control-free baseline differ from controlled path? | INC-001 regression |
| State integrity | Does drift get detected? | `evals/state/state-integrity.sh` |
| Freshness | Are Tier 3 results recent and non-reused? | `evals/skills/evidence-freshness.sh` |
| Integration | Does the harness remain healthy? | `evals/maintenance.sh` |
| Independent review | Does a fresh context find material defects? | `code-reviewer` review path |

F7's closure record reports `maintenance.sh` 12/12 PASS, all F7 fixtures,
INC-001, state integrity, skills validation and syntax checks passing. It also
records a change-budget variance: POST-F7 reports 591 additions/17 deletions
and seven fixture files; an independent scoped recount measured 608 additions/
18 deletions. The variance was documented and accepted rather than silently
rewriting the audit.

### Script versus native verification

`SCRIPT VERIFIED` means a repository script and its fixture executed in the
available environment. It does not mean the Claude Code event dispatcher

## 20. F8 Audit Limitations

The following limitations were preserved rather than treated as automatic
defects:

### Native TaskCompleted lifecycle

The TaskCompleted script and fixture are verified directly, but OpenCode did
not exercise the native Claude Code TaskCompleted dispatcher. A native event
failure is not inferred from the absence of native access.

### Malformed native JSON path

The script can be called with malformed input and fails closed. The normal
Claude Code wire shape was not available to prove that native dispatch would
produce malformed input or how it would route it. Script boundary testing and
native wire testing are separate questions.

### Valid non-object JSON roots

The firewall validates a single JSON document, not a full object schema for
every possible JSON root. No evidence shows normal Claude Code Bash input is a
scalar or array, and no current incident depends on one. This remains a policy
boundary, not a proven runtime defect.

### Finite firewall coverage

The regex set covers demonstrated and reviewed command families. It does not
claim arbitrary shell obfuscation protection. A future documented bypass would
be new evidence; the finite boundary itself is intentional.

### Reviewer identity

The reviewer convention is documented, but the schema does not prove a model's
identity cryptographically. The reports correctly avoid treating a reviewer
label as cryptographic proof.
